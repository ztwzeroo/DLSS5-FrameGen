## 必须优先修复

### R1 · P1：首次安装失败没有恢复原 INI

位置：`src/dlss_combo/install.py:172`、`:213`。

游戏目录原本有 INI，第一次安装先备份并覆盖它；若后续 DLL 写入失败，异常处理删除新 INI，但只还原 `deleted` 列表中的旧受管文件，没有还原首次备份的用户 INI。实测结果是原 INI 从游戏目录消失，manifest 尚未创建，正常 uninstall 无法恢复。原内容仍在 `.pre.bak`，不是永久丢失，但需要手动找回。

修复：把首次覆盖也登记到同一个回滚事务，在每个失败点恢复安装前字节内容；恢复失败保留可读恢复清单并准确报告。验收至少覆盖 DLL 写失败、manifest 写失败、备份写失败及重装失败。

### R2 · P1：卸载另存旧配置会覆盖其他文件

位置：`src/dlss_combo/uninstall.py:42`。

用户修改当前 INI 后，卸载会把安装前配置另存成固定名称 `dlssg_sm86.ini.pre-existing`，但没有检测该名称是否已存在。独立复现确认同名用户文件被覆盖；如果该路径是符号链接，复制还会覆盖游戏目录外、当前进程有权限写入的目标文件。

修复：排他创建不冲突的新副本，验证新输出路径及链接；任何现有文件都不能无条件覆盖。卸载前统一检查全部恢复目标，恢复成功后才清理备份。

### R3 · P1：临时文件处理仍可越界写入并删除无关文件

位置：`src/dlss_combo/install.py:43`、`:49`、`:216`、`:224`；`src/dlss_combo/manifest.py:91`。

临时名称固定为 `目标名.dlsscombo-tmp`。复现：预先存在的临时路径符号链接使写操作改动目录外文件。安装成功/失败时还按通配符删除所有同后缀文件；复现中无关的 `unrelated.dlsscombo-tmp` 被删除。

修复：使用同目录随机、排他创建的临时文件，仅清理本次操作登记的路径；验证所有输出父目录，覆盖首次安装的 metadata/backup 路径。需要 Windows 链接/目录联接场景的补充验证；本轮链接案例在 macOS 临时目录复现，不声称已在 Windows 实测。

### R4 · P1：Linux 包最低 glibc 要求标错

位置：`.github/workflows/release.yml:84`、`:204`；README Linux 部分；实际包的 build-info.txt。

CI 对整个单文件程序直接搜索字符串，结果只有 `GLIBC_2.14`，据此推荐 `glibc >= 2.17`。但内嵌共享库被压缩，搜索外层文件不能得到真实依赖。[PyInstaller 官方说明](https://pyinstaller.org/en/stable/operating-mode.html#how-the-one-file-program-works)明确解释了单文件包内的压缩共享库。

本轮实际下载 ZIP，读取 PyInstaller CArchive、解压共享库，并解析 ELF `.gnu.version_r` 的依赖版本，得到：

| 内嵌库 | 最高 GLIBC 版本需求 |
|---|---|
| libpython3.13.so.1.0 | GLIBC_2.35 |
| libcrypto.so.3 | GLIBC_2.34 |
| liblzma.so.5 | GLIBC_2.34 |
| libffi.so.8 | GLIBC_2.27 |

因此当前包的 glibc 必要下限至少是 **2.35**；达到该值也不等于所有发行版均已验证。中文 release 注释写 2.35，英文与 build-info 写 2.14/2.17，互相矛盾。

修复：对实际解包后的 ELF 依赖版本做检查，并在承诺的最低环境运行最终程序；若要支持更旧系统，在该基线环境重建并测试。发布更正版本，避免静默替换同标签附件。

## 后续可靠性问题

### R5 · P2：原始备份缺失时仍清空卸载状态

位置：`src/dlss_combo/uninstall.py:36`。

备份记录存在但备份文件丢失时，卸载静默跳过恢复，删除受管 INI 和 metadata，返回正常动作列表。复现成立。应在任何删除前验证必需备份存在且完整；异常时保留恢复记录。建议为原始备份记录 SHA256，并校验备份类型与结构。

### R6 · P2：新会话没有路由事件时沿用旧成功日志

位置：`src/dlss_combo/doctor.py:66`。

最新日志只包含启动事件、旧日志含 `route.active=true`，doctor 仍报告“已生效”。虽然显示来源文件名，但没有说明是历史会话，用户可能以为本次安装/本局成功。

修复：以最新会话为诊断范围；没有当前事件则显示“未验证”，历史成功单独标明时间。区分文件安装正常、代理被加载、路由已启用、游戏画质确认四个层次；加可导出的结构化诊断。

### R7 · P2：下载刷新中断破坏原本可用 kit

位置：`src/dlss_combo/fetch.py:112`。

每个文件下载完成即覆盖旧文件，所有文件完成后才写 metadata。复现第二个下载请求失败后，旧 kit 已出现哈希不匹配。当前安装会拒绝损坏 kit，保护有效，但离线回退能力丢失。

修复：新版本放入独立 staging 目录，全部校验后切换版本索引；失败保留旧 kit。安装、卸载及缓存刷新还应加入相应目录锁，避免并发操作混用状态；并发问题本轮仅做设计检查，未声称已动态复现。

## 面向欧美玩家的介绍与使用体验

1. **先补英语操作体验。** README 英文化了，但 `--help`、动作提示、失败原因和修复建议仍大量中文。增加统一文案层、默认英文与中文切换；错误同时给出明确下一步。
2. **明确 EXE 是命令行版。** 已经无需安装 Python，但仍要求终端操作，不能宣传成双击安装向导。建议后续做小型界面：选择游戏 → 检查 GPU/冲突 → 预览改动 → 安装 → 验证/恢复，并复用现有核心逻辑。
3. **整理下载入口。** 当前 [Latest](https://github.com/ztwzeroo/DLSS5-FrameGen/releases/latest) 仍是旧 v0.1.0，而 [v0.1.1](https://github.com/ztwzeroo/DLSS5-FrameGen/releases/tag/v0.1.1) 是预发布。首页明确推荐的预览版本、Windows 主入口及 Linux 实验入口；在旧版说明迁移原因。
4. **统一示例。** 新手示例不应普遍带 `--arch sm86` 强制覆盖，应先自动检测；仅探测失败且用户确认硬件时使用。Linux 指南补全 fetch、实际代理名称和权限步骤；README 把 Steam 游戏目录概括成总在 prefix 的 drive_c 下，应删除这个过度假设。
5. **真实操作演示优先于继续加装饰。** 首页放短操作录屏或真实界面截图，紧邻三步快速开始、兼容性表、恢复方式。现在没有 GUI，图片不能假装成已交付界面。
6. **用实测建立可信度。** 按 GPU、驱动、游戏版本、分辨率、运行库、组合方式列成功与失败；分别展示原版、画质层、插帧层和组合的同场景结果。没有实测时维持“未知”，不发布推算 FPS。
7. **清理状态页。** README/STATUS 仍写 107 tests；STATUS 前部两个 review 链接缺 `reviews/`；已修复与未修复叙述混杂，末尾对旧 repro 成功含义仍写反。把“特定回归通过”和“全部文件安全已解决”分开。

这些是基于当前项目的改善建议；本轮没有进行 GitHub 同类 Top 10 排名调研，也不把此前参考项目视为当前排名依据。
