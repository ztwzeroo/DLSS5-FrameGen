# dlss-combo 全面审查与改善建议

审查日期：2026-09-20。基线：`9e55ebb`。审查时工作区干净。结论：**建议修改后再发布；目前适合作为实验性原型，不宜对普通用户承诺安全安装、完整还原和组合效果已验证。**

本项目负责下载组件、选择代理、写入配置和诊断，不实现渲染算法。模块划分清楚，纯标准库运行时、网络/GPU 适配器可替换、默认避开 dxgi、离线临时目录测试等设计值得保留。当前最重要的投入是文件安全与真实兼容性验证。

## 1. 检查范围与证据边界

- 检查全部 12 个 Python 源文件、测试、README、设计文档、包配置和提交记录。
- 原有测试：**81 passed in 0.32s**，macOS / Python 3.14。本结果证明离线测试通过，不证明 Windows 游戏内插帧、画质或性能效果。
- 在临时源码副本中使用正常隔离构建成功生成 wheel，并在仓库外以隔离解释器从该 wheel 调用 CLI，版本输出 `dlss-combo 0.1.0`、退出码 0。未做 Windows 安装后启动测试。最初禁用构建隔离的尝试因本地缺 setuptools 失败，正常构建已解决，未归类为产品缺陷。
- 新增独立复现脚本 `2026-09-20-repro.py`，9 个问题行为全部复现。它只操作自动清理的临时目录；没有执行真实 DLL 或 EXE，也没有触碰实际游戏文件。
- 核对两个上游项目的公开说明，以及 dlssg 的 INI、安装和代理说明。上游文档自身部分表述不一致，需要针对固定 commit 建立兼容性规则。
- 实时解析上游 commit：`9621db573e07ed54f50c15bbb585ed9a7bdfac28`。抽查 7 个下载路径的 HTTP HEAD 均为 200；这只证明路径可访问，不证明文件内容、签名或游戏兼容性。
- 没有运行 Windows/NVIDIA 真机测试，没有测 FPS、延迟、显存、图像质量，也没有完成真实上游二进制安装。
- 本次交付为审查报告和复现证据；未修改产品源码。

## 2. 发布前必须修复（P1）

### A. 卸载信任 manifest 路径，能够删除游戏目录外的文件

位置：`src/dlss_combo/uninstall.py:18`、`:24`；`manifest.py:66`。

`files[].path` 直接拼接后删除，`backups[].original/saved_to` 直接拼接后复制，没有路径范围、字段类型、schema 版本或归属检查。临时清单写入 `../outside-sentinel.txt` 后，卸载实际删除了游戏目录外的测试文件。绝对路径也未拒绝。重装已有代理白名单保护，卸载没有同步采用。

建议：统一清单验证入口；只接受允许管理的文件名，备份必须在受控目录内；拒绝绝对路径、父目录跳转、符号链接及 Windows junction/reparse point 越界；校验完整后才能开始任何修改。损坏或未知版本清单不得触发猜测性删除。此问题需要本地清单被修改或导入错误数据作为触发条件，不属于已证明的远程漏洞。

验收：相对越界、绝对路径、非法备份目的地及 Windows 链接场景全部拒绝，目录外哨兵字节不变。

### B. 只按文件名认定归属，覆盖第三方替换文件

位置：`install.py:80`、`:108`；`scan.py:25`；`uninstall.py:18`。

用户安装后，用另一个 mod 替换 `version.dll`，旧 manifest 仍把这个名字认作本工具文件。重装会覆盖新 mod；随后卸载会删除同名文件及备份。该链路已复现。直接卸载同样没有修改前哈希检查。

建议：破坏性操作前比较当前哈希和安装时哈希。对变化文件标记“外部修改”，保留原件并返回冲突结果。DLL 与用户可编辑 INI 采用不同管理策略。备份记录明确区分“首次安装前原件”和“本工具历史版本”，不能靠是否与当前文件同名推断。

验收：安装后替换 DLL，再分别重装和卸载；第三方文件都必须保持不变。

### C. 首次安装覆盖已有 INI，卸载无法还原

位置：`install.py:126`。

备份仅处理旧 manifest 中的文件。用户此前手工配置过 `dlssg_sm86.ini`，首次安装会直接覆盖，卸载后原文件消失。该行为已复现。

建议：写入前记录文件原始状态。已有 INI 应先备份，或保留非本工具管理的配置键。跨多次升级持续继承最初备份，卸载还原首次安装前状态。

验收：带自定义配置的目录执行安装→重装→卸载，原配置逐字节一致。

### D. 文件哈希缺失仍通过校验，缓存程序启动也跳过校验

位置：`fetch.py:108`、`:138`、`:191`；`tests/conftest.py:19`。

`verify_kit` 只比较已存在的哈希项，`files={}` 仍通过；安装测试普遍使用这种夹具，因此改坏 DLL 后重装成功的测试反而固定了漏洞。Swapper 缓存命中和启动只检查文件存在；复现中修改 EXE 后仍被传给启动器，未实际执行它。

建议：每个必需文件都必须有格式正确且匹配的 SHA256；缓存命中也校验，启动前再次校验。下载时自行计算哈希只能建立本地完整性基线，应与上游提供的校验值/签名区分，界面展示验证来源。不能宣称自行计算摘要等于上游真实性验证。

最低修正示例：

```python
expected = recorded.get(kit_rel)
if expected is None:
    problems.append(f"missing checksum: {kit_rel}")
elif Manifest.sha256_of(p) != expected:
    problems.append(f"hash mismatch: {kit_rel}")
```

还需要补充摘要格式和元数据结构验证。测试夹具生成真实摘要；模拟升级应使用新的合法 kit，而不是随意改字节继续通过。

### E. 回滚不覆盖写了一半才失败的情况

位置：`install.py:129`、`:133`、`:138`；`manifest.py:47`。

文件复制完成后才登记到 `created`。复制中途写出部分字节再报错，目标不会清理；回滚又只恢复“不存在”的文件，损坏目标仍存在便不会恢复。模拟磁盘满后，原 DLL 被 `PARTIAL` 留在原路径，已复现。现有回归测试在写入前报错，没有覆盖这种情形。manifest 直接写入，写清单失败也可能损坏旧清单。

建议：先生成并验证全部暂存文件，记录事务日志和旧状态，用同目录原子替换提交；清单最后原子提交。回滚按操作记录恢复，不依赖文件是否存在。备份使用独立事务目录，保留失败恢复资料。添加安装/卸载互斥锁。

验收：备份、INI 写入、DLL 部分写入、清单写入、回滚自身失败分别做故障注入；不能只测成功路径和写入前异常。

## 3. 应尽快完善（P2）

### F. 下载缓存不是事务，多运行库来源记录不准确

位置：`fetch.py:71`、`:80`、`:88`。

- 缓存命中仅检查文件存在，损坏缓存不会自动修复。
- refresh 直接覆盖现有文件，中断可能留下新旧混合的缓存，旧版本不能继续稳定使用。
- 重建 kit.json 会丢失 Swapper 元数据，已复现。CLI 后续重新下载 Swapper 成功可以重建，但下载失败时缓存文件仍在，启动入口却丢失。
- 310.1 / 310.9 共用一个 commit 字段：在不同时间获取两个运行库后，旧运行库也可能被标成新 commit。

建议：每个组件、运行库分别记录来源 commit/tag、文件摘要、下载时间和校验来源；下载至暂存目录，完整校验后切换。保留其他组件元数据，支持固定版本和明确升级。增加重试、进度、超时和磁盘空间提示，较大文件用流式下载。

### G. doctor 可能误报成功

位置：`doctor.py:15`、`:49`、`:78`；`cli.py` 的 doctor 分支。

- 同一日志取第一条 route；先 true 后 false 时仍报告成功，已复现。
- 最新日志无 route 时会沿用旧日志的成功状态，未标出这是历史结果。
- `bool("false")` 得到 True；JSON 根不是对象时可能异常，应严格解析布尔值和结构。
- 任意空 `reshade-shaders` 文件夹便报告 DLSS 5 画质层已安装，已复现。ReShade/RenoDX 痕迹不能单独证明 DLSS 5 组件齐全或游戏内生效。
- 检测出坏哈希或 route=false 后，CLI 仍返回 0，不利于自动验收。

建议：区分“文件已安装”“本次启动代理已加载”“帧生成路由已激活”“画质效果已验证”；显示证据时间、日志路径和实际代理。按本次会话的最新有效事件判断，大日志流式/尾部读取。返回结构化状态和有意义的退出码；增加 `doctor --json` 和诊断报告导出。

### H. 代理名空闲不代表游戏会加载；d3d12 回退过早

位置：`proxy_select.py:4`；`install.py:83`。

当前只取首个空闲名，version/winmm 都被占用时会优先选 d3d12，早于 dbghelp/dinput8。没有验证游戏是否导入或实际加载选中的代理。

当前上游 alternatives 说明把 d3d12/dxgi 作为工具类代理未加载后的特殊回退；同族多代理的 standby 机制也不能扩展为“任意第三方 DLL 天然共存”。[上游代理说明](https://github.com/sdli1995/dlssg_for_sm86/blob/main/alternatives/README.md)

建议：先采用较低风险工具代理候选顺序，并提供 `--proxy` 显式选择；未加载时通过 loader 日志指导切换。d3d12/dxgi 使用单独的显式选项。保留单代理策略可以，但必须说明它是项目选择，并建立生效验证，不能当作已证明的通用最佳方案。

### I. 预检与参数实际能力不一致

位置：`gpu.py:79`；`install.py:43`；`ini.py:50`。

- `--arch` 直接返回，连驱动探测也跳过，而快速开始默认给了该参数。
- 非 Windows、空目录、未知 GPU 可以继续落盘；未验证渲染 EXE、x64/D3D12/原生 FG 条件。
- 多 GPU 只读第一行，没有目标 GPU 选择。
- 310.1 接受 `--mfg 6x` 并报告安装成功，但上游 INI 明确 310.1 最高 4X。[上游 INI](https://github.com/sdli1995/dlssg_for_sm86/blob/main/dlssg_sm86.ini)

建议：平台和架构、驱动分别检查；架构覆盖不应自动屏蔽驱动信息。维护运行库能力表，对不支持的组合拒绝或明确降级。预检输出“支持/不支持/未知”，无法静态确认的游戏能力不要伪装成已确认。提供模拟安装方式供跨平台开发测试。

### J. Swapper ZIP 和 EXE 没有完整区分

位置：`fetch.py:146`、`:191`。

下载器同时接收 portable.zip 和 portable.exe，启动器却直接打开所记录路径。ZIP 在 Windows 上通常只是打开压缩包，不代表 Swapper 已启动。建议分开描述资产类型；ZIP 经过路径安全检查后解压并定位允许的 EXE，或者明确提示手工处理。上游资产名/本地缓存路径也应限定在 kit 目录内，摘要文件解析兼容常见的 `*filename` 标记。

## 4. 测试与工程质量

现有测试覆盖正常安装、第三方代理占用、参数校验、网络替身、基础哈希比较，具备继续改进的良好基础。但 81 个通过不等于核心安全保证成立。

建议补充以下行为验收：

| 范围 | 重点断言 |
|---|---|
| 所有权/还原 | 外部替换 DLL 保留；自定义 INI 跨升级还原；越界清单完全拒绝 |
| 写盘故障 | 部分写入、清单写失败、进程中断后可恢复 |
| 下载 | 元数据缺摘要失败；损坏缓存重取；刷新失败保留旧 kit；两个 runtime 独立来源 |
| 诊断 | 多日志/多事件/陈旧日志/错误类型/巨型日志；普通 ReShade 不报 DLSS 5 成功 |
| Windows | 占用 DLL、权限拒绝、大小写、中文与空格路径、长路径、junction、并发安装 |
| 发布包 | 构建 wheel；在干净环境安装后从仓库外运行 CLI |
| 真机 | RTX 20/30 × runtime × 代理；新装、重装、卸载、原游戏恢复 |

仓库未见 CI 工作流。建议配置 Windows 为必需测试平台，同时保留跨平台纯逻辑测试；覆盖声明的 Python 3.10 最低版本及当前版本。将 pytest/构建/静态检查工具列入开发依赖，固定可复现的开发环境，增加基础 lint。覆盖率用于发现分支遗漏，不把数字作为替代真实行为验收的目标。

README 写 67 个测试，实际为 81；快速开始没有明确 `python -m dlss_combo` 需要先安装包或设置 src 路径。推荐给出 `pip install -e '.[dev]'` 风格开发流程（需先定义 dev extra），与 `pipx install .` 的用户流程分开。补充 `--runtime`、`--kit-dir`、`--launch-swapper` 的完整帮助和失败示例。

## 5. 产品与架构改善路线

### 第一阶段：把安全闭环做实

优先完成 A–E，修正测试夹具，并补充 Windows 文件系统测试。验收标准是“无关文件不变，失败可恢复，缺证据不通过校验”。暂不扩大界面或功能范围。

### 第二阶段：让用户知道发生了什么

增加 `install --dry-run`，预览目标 EXE、选择的代理、要新建/保留/修改的文件、备份位置和未知兼容性；增加独立 `status`，列出游戏目录、已装版本、当前哈希及备份状态。完成结构化 doctor、分组件缓存元数据和安全升级。

建议内部采用“计划→验证→执行→提交清单”四步，把纯决策和文件操作分开。模块规模目前不大，不需要引入复杂插件框架或重写语言。

### 第三阶段：建立可信的游戏兼容性记录

选择少量目标游戏，记录游戏版本、GPU、驱动、代理、上游 commit、runtime、显示设置和真实日志。分别测原版、仅画质层、仅插帧层、组合四组；记录基础 FPS、1% low、延迟、显存、伪影和稳定性。当前会话未取得这些测量，不能给出提升百分比或普遍共存保证。

DLSS5-Swapper 上游自身包含多种安装路线和组件管理，本项目应集中提供组合兼容性、冲突保护、可靠还原及验证价值。[Swapper 项目说明](https://github.com/rakanki911/DLSS5-Swapper)

### 第四阶段：降低使用门槛

在安全与真机验证完成后，再考虑签名的 Windows 独立程序或简单安装向导。先展示“已安装/待游戏验证”的区别、故障恢复入口和卸载范围。调整“一条命令装好”“天然共存”等文案，准确说明画质层仍需 Swapper 内操作，本工具卸载主要负责自己的插帧层。

## 6. 待产品决策确认的事项

这些问题不影响本次审查结论，但影响后续实现：是否允许管理已被用户改动的配置；默认固定经过测试的上游版本还是持续跟随 main；首批支持哪些游戏；产品成功条件是“文件落盘”还是“本次游戏运行验证通过”。建议默认保护用户修改、固定已验证版本、从少量游戏建立证据，再扩大支持。

## 7. 复核方法

在项目根目录运行：

```sh
.venv/bin/python -m pytest -q
.venv/bin/python docs/reviews/2026-09-20-repro.py
```

复现脚本中的 `observed=true` 表示问题行为仍然存在，不是安全测试通过。修复后应把相应场景迁入正式测试，改为断言文件保留、校验拒绝及准确状态。脚本仅使用假文件和网络替身，不下载或启动真实程序。
