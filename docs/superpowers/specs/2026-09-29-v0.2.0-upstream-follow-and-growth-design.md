# v0.2.0 — 上游跟随与增长设施设计（upstream follow & growth）

日期：2026-09-29 · 状态：已与用户确认范围（全部 6 项、CLI 全英文化、方案 A：单一 spec、子代理并行、一次发 v0.2.0）

## 背景与目标

v0.1.3 的文件安全层已闭环（122 测试、四轮审查），但存在三个结构性短板：

1. **上游跟随是被动的**：安装器装时动态拉上游最新（dlssg 取 main HEAD、Swapper 取 latest release），但上游若改文件名/资产命名/INI 键位，我们只能在用户报障后才知道。
2. **反馈漏斗断裂**：发布近两周 0 个 issue、全部版本累计约 25 次下载；game-test 模板存在但测试者要自己找日志、自己组织报告，摩擦过大。
3. **目标人群覆盖缺口**：`gpu.py` 只解析 nvidia-smi 第一行，多 NVIDIA GPU 机器（如 GT 710 输出 + RTX 3060 计算）会取错架构；STATUS 遗留的 doctor 语义与代理名顺序问题未修。

本轮目标：把"他们更新我们跟着更新"变成每日自动监控；把"报一次结果"的成本降到一条命令；修掉已知诊断缺陷；CLI 面向国际测试者全英文化。**真机游戏内验证仍不在本轮范围**（需要 RTX 20/30 硬件），本轮只做前置设施。

## 非目标

- 不做 CLI 双语切换（已决策：全英文，README.zh-CN.md 文档保留中文）。
- 不做二进制自动更新（`--check-update` 只提示，不下载不替换）。
- 不改 doctor/install/uninstall 的文件安全语义（已闭环，避免回归面）。
- 不碰源码内部中文注释（非用户可见，翻译徒增 diff 风险）。

## 工作流划分

六条互相独立的工作流 + 文档资产收尾。版本 **v0.2.0**（CHANGELOG：Added×4、Changed×1、Fixed×2）。

### W1 上游跟随监控

**新增** `.github/workflows/upstream-check.yml`：

- 触发：`schedule: cron "17 6 * * *"`（每日 UTC 06:17，避开整点）+ `workflow_dispatch` + 对 workflow 文件与脚本自身的 push（paths 过滤）。
- 权限：`contents: read, issues: write`。
- job（ubuntu-latest + Python 3.13）：`python scripts/upstream_check.py`；退出码非零时用 `gh` CLI（`env.GITHUB_TOKEN`）幂等开 issue——查找仍 open 的固定标题 `[upstream-check] upstream structure drift`，存在则追加带 run 链接的评论，不存在则创建并把脚本输出贴进正文。成功时若该 issue 存在则自动关闭并评论恢复。
- README.md 顶部加 workflow badge（upstream-check pass/fail）。

**新增** `scripts/upstream_check.py`（纯标准库，可直接 `import dlss_combo` 复用其逻辑）：

检查项（对应"上游结构没漂移"而非"上游哈希可信"——dlssg 哈希是我们自算自记的，上游不发布校验文件）：

1. `GET api.github.com/repos/sdli1995/dlssg_for_sm86/commits/main` 能解析出 commit sha；
2. 两个运行库（310.9、310.1）各自对 `dlss_combo.fetch.kit_files(runtime)` 列出的**每个仓库路径**，`raw.githubusercontent.com/<repo>/<sha>/<path>` 返回 200 且非空；
3. 下载到的上游 `dlssg_sm86.ini` 用 `configparser` 可解析，且含我们模板所镜像的节与键（`[General].Enabled`、`[FrameGeneration].Optimized`、`[FrameGeneration].MaxGeneratedFrames`、`[Runtime].Mode`）——键集合从 `dlss_combo.ini` 导出的常量取，不在脚本里重复硬编码；
4. `GET api.github.com/repos/rakanki911/DLSS5-Swapper/releases/latest` 返回的资产里，按 fetch.py 的 portable 资产匹配规则能选中恰好一个（必要时把该匹配逻辑提为 `fetch.py` 内可复用函数）。

失败时输出英文人话摘要（哪一项、实际值、期望值）并 exit 1；全部通过 exit 0。

`--selftest` 模式：不联网，用注入的本地 fixture（正常 / 每种失败各一）驱动同一套检查函数，断言判定正确。`ci.yml` 增加一步跑 `python scripts/upstream_check.py --selftest`，保证监控脚本本身不烂。

### W2 `report` 命令（反馈漏斗）

**新增** `src/dlss_combo/report.py`：`build_report(game_dir, kit_dir=None, runner=None) -> str`，纯只读、完全离线，产出一段可整段粘贴到 game-test issue 的英文 markdown：

- 工具版本与平台（`platform.platform()`）；
- 安装清单摘要（有 manifest 时：代理 DLL 名、mfg、runtime、上游 commit、已装文件数；无 manifest 时明说 "not installed by dlss-combo"）；
- doctor 摘要（复用 doctor 的返回结构：路由事件、画质层证据分级、结论；**不重复实现解析**）；
- GPU 清单（来自 W3 的 `detect_all_gpus`，逐卡列出 name/arch/driver 与被选中的主卡）；
- kit 缓存状态（各 runtime 是否就绪、commit）；
- 固定的诚实块 "What this report does NOT contain"（无帧率/画质/延迟实测，与 STATUS 口径一致）。

CLI：`dlss-combo report GAME_DIR [--out FILE]`——默认打印到 stdout 并附 game-test issue 链接与粘贴说明；`--out` 写文件；**绝不自动开浏览器、绝不上传任何东西**；报告生成成功即 exit 0（doctor 发现的问题不导致 report 失败——report 是取证不是判定）。

### W3 多 GPU 枚举

重构 `gpu.py`（保持现有公开签名 `detect_gpu(override, runner)` 兼容）：

- `_parse_nvidia_smi_all(text) -> list[GpuInfo]`：解析 CSV 全部数据行；行内 name 不以 NVIDIA 开头的整行跳过（与现状一致的防御）。
- `detect_all_gpus(runner=None) -> list[GpuInfo]`：nvidia-smi 失败返回 `[]`。
- `choose_gpu(gpus: list[GpuInfo]) -> GpuInfo`：NVIDIA 行里**优先取第一块架构受支持（sm75/sm86）的卡**；没有受支持卡则取第一块 NVIDIA；列表空返回 unknown。选择规则是确定性的，不做交互式选择（保持 CLI 可脚本化），多卡有歧义时在输出里列出全部卡并建议 `--arch` 显式覆盖。
- `detect_gpu` 改为 `choose_gpu(detect_all_gpus(runner))` + override 分支不变。
- doctor 输出在检测到 >1 块 NVIDIA 卡时列出全部卡与被选主卡。

测试 fixture 至少覆盖：单卡；GT 710 在前 + RTX 3060 在后（必须选中 3060）；RTX 4090 在前 + RTX 3060 在后（必须选中 3060 而非 4090）；两块都不受支持；乱文/空输出。

### W4 `--check-update`

**新增** `src/dlss_combo/update.py`：

- `parse_tag(tag) -> tuple[int, ...]`：`v0.2.0` → `(0, 2, 0)`，容错非数字段。
- `check_update(current: str, fetch_bytes=None) -> UpdateInfo`：调 `api.github.com/repos/ztwzeroo/DLSS5-FrameGen/releases/latest` 取 `tag_name` 与 `html_url`；10 秒超时；任何网络/解析错误 → `status="unknown"`（**不抛出**）。
- CLI 顶层 flag `--check-update`：执行检查并打印结果（`up to date` / `available: <tag> <url>` / `unknown (network error, skipping)`），然后继续执行所给的子命令（可与任何子命令组合，不阻塞）；单独使用时检查完 exit 0。

### W5 STATUS 遗留修复

(a) **doctor 会话语义**：诊断范围仍取最新日志（R6 已定），但会话内判定改为取**最后一个路由事件**为准（无论成败），不再被更早的成功事件覆盖；ReShade/RenoDX/Feeder 标记降级为独立证据级 "files present (not proof of an active layer)"，不得计入画质层生效判定；doctor 的任何解析失败必须置 `has_problems=True`（现状允许解析失败仍 exit 0，对齐 STATUS 所述缺陷）。

(b) **代理名回退顺序**：实现第一步先核对上游 README/INSTALL 的 alternatives 推荐顺序并在代码注释记录出处与核对日期。若上游给出明确顺序，按上游；若上游无明确顺序，采用 `ALT_NAMES = ["winmm", "dbghelp", "dinput8", "d3d12", "dxgi"]`（d3d12 降为倒数第二：原生 d3d12.dll 是 D3D12 运行时本体，代理它风险最高；dxgi 仍最后，`--allow-dxgi` 门控不变）。新增测试断言顺序常量与"按序取第一个空闲名"的安装行为。

## 错误处理原则

- 所有新网络路径（W1/W4）超时 10–120s 分级、任何失败降级为可读英文消息，不抛裸 traceback 给用户。
- report/doctor 保持只读：任何输入缺失都反映在输出里（"not installed"），不以异常终止。
- W1 的 issue 自动化必须幂等（同标题复用），避免每日 cron 刷屏。

## 工程铁律（沿用项目既有约束）

动手前 `git fetch` 对账并行改动；测试全绿才提交；推送走 SSH；一切文本 IO 显式 `encoding="utf-8"`；版本号单源（`__init__.py` 字面量 + pyproject dynamic）；上游文件绝不硬编码字节数（监控只看结构键，不看内容哈希）。
